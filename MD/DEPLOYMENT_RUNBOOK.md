# Deployment runbook

No deployment has been performed. Follow these steps in an approved staging project first.

1. Import this complete source into the intended GitHub repository/branch only after owner approval. Preserve existing history, review the changed-file manifest and enable required CI checks. No push/merge was authorized or performed here.
2. Configure the Next.js host with Node 24, npm ci and npm run build. For Vercel, set the application root to the folder containing package.json. Configure Supabase public URL/key and server-only service/provider/payment secrets using the environment dashboard. Set the staging HTTPS NEXT_PUBLIC_APP_URL. Keep sending disabled. Secrets must not be committed or included in public-prefixed variables.
3. Back up the target database and review its applied migration history. Apply only missing migrations in sequence. Confirm RLS and function grants on hosted Supabase with separate owner, company A, company B and viewer accounts. Bootstrap the first owner using reviewed SQL; no default password or owner identity is embedded.
4. Configure Supabase Auth Site URL and allowed redirect URLs for the actual staging/production origins and /auth/callback. Verify email confirmation, sign-in, session refresh and sign-out. Review auth email branding separately from website CMS branding.
5. Run npm run check:release with complete staging settings. The source environment is deliberately unconfigured; its expected failure is not a failed application build. Verify that public pages, fallback CMS copy, legal routes and private route guards work. Publish a controlled CMS change and verify that other sessions see the published copy while drafts stay private.
6. Configure Paystack test-mode webhook /api/billing/webhook and use the documented canonical origin for the return URL. Confirm successful payment, wrong amount/currency, replay and failed payment handling. Reconcile old pending transactions. Never enable live charges before operator acceptance.
7. Configure one email provider, validate DNS ownership/authentication, consent and company postal address, set conservative provider/plan budgets and register the signed/token-authenticated webhook. In a controlled staging send window, temporarily enable delivery and test only operator-authorized consenting recipients. Return it to disabled until approval. Verify acceptance separately from actual delivery and one-click unsubscribe. Review timeout/unknown behavior without manually resending uncertain messages.
8. Provision a trusted external worker scheduler using the authenticated POST described in Batch 9. Test retries, paused runs, company suspension, quota exhaustion and recovery. Monitor failed requests, unknown outcomes, paused runs and webhook persistence failures. Health endpoint is liveness only; it does not test Supabase, DNS or provider availability.
9. Complete LIVE_ACCEPTANCE.md, a restore rehearsal and desktop/mobile browser checks. Avoid caching nonce-bearing HTML; test CSP/hydration and all form/CSV workflows. Review remaining tooling and feature limitations before launch.
10. Only after the owner accepts staging, promote approved source/configuration to production, confirm live keys and origin, repeat read-only access checks, then enable billing/sending intentionally. Record deployment, migration, verification and rollback evidence. An actual publication still requires the owner's authorization.

CI covers local source gates and production dependency advisories. It does not perform live acceptance, migrate a hosted database, send campaigns or deploy.
